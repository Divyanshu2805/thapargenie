# Coding conventions

Match the code around a change before anything written here.

## Backend

**Layout.** Each Django app keeps the same files:

| File | Holds |
|---|---|
| `models.py` | Tables, with choices and length limits repeated as database constraints |
| `services.py` | Writes that must be validated and audited. Views call these; they never write through the ORM directly for an audited change |
| `views.py`, `serializers.py`, `urls.py` | The student API |
| `admin_views.py`, `admin_serializers.py`, `admin_urls.py` | The staff API, every view a subclass of `AdminAPIView` |
| `retention.py` | What `purge_data` removes for this app |
| `management/commands/` | Command-line entry points; logic stays in importable modules |
| `tests/` | One file per area |

**Boundaries between apps.** `rag/pipeline.py` saves nothing and imports nothing from
`chat`; persistence belongs to `chat/answering.py`. Only `rag/llm` imports a model SDK,
and only `api/firebase.py` talks to the Firebase Admin SDK. Reach another app through its
services or models, never its views.

**Views** stay thin: authenticate (the defaults do it), validate with a serializer, call a
service or a query, return a payload. Student querysets start from
`Conversation.objects.owned_by(request.user)` or filter on `conversation__user`.

**Serializers** for input reject unknown fields (`RejectUnknownFieldsMixin`) and cap every
length. Output is built by small `*_payload` functions, so nothing leaves the API by
accident.

**Errors** are `APIException` subclasses with a `default_code`, or
`common.admin_api.error_response` when extra fields are needed. A message is a sentence a
student or admin can read; internals go to the log.

**Tunables** are named constants at the top of the module that uses them (`KEEP`,
`BUDGET_TOKENS`, `MAX_DISTANCE`), or environment variables in `settings/base.py` when they
differ between environments, or `ChatSettings` when an admin should change them at runtime.
A number in the middle of a function is a bug waiting for a second copy.

**Style.** `ruff` with `E`, `F`, `I`, `B`, `S` and `DJ`, 100 columns, Python 3.13. Single
quotes in application code. A module opens with a docstring that says what it is for and
why it is shaped the way it is; comments explain reasons, not mechanics. A lint suppression
carries its reason on the same line.

**Migrations.** One per change, generated by Django, backwards compatible: add a column as
nullable first, remove it in a later release.

### The auth code

`api/` (authentication, identity, permissions, errors), `userauths/`, and in the web app
`src/auth`, `src/views/auth`, `src/utils/apiClient.js`, `auth.js` and `session.js` hold the
sign-in code. It is changed only on purpose, with its own review: improvements are proposed
first, and behaviour is extended from outside where possible, for example
`common/errors.py` wraps the auth app's exception handler instead of editing it, and
`access/policy.py` is plugged in by an import path.

## Frontend

**Layout.** One folder per feature under `src/features/`, with its tests beside the files
they cover (`Message.jsx`, `Message.test.jsx`). Shared UI is in `src/components`, API calls
in `src/lib/api`, and primitives from shadcn/ui in `src/components/ui`.

**State.** Server data lives in TanStack Query; a mutation invalidates the queries it
affects. Local state stays in the component. There is no global store.

**Requests.** JSON calls go through `apiRequest` in `src/utils/apiClient.js`; streams and
uploads go through `src/lib/http.js`. Both attach a fresh token, send a request id and
turn the API's error envelope into an `ApiError` with a `code`. Components branch on
`code`, never on message text.

**Loading.** The first screen is one bundle; every other page is `lazy()` in `App.jsx`.
The admin area is its own chunk.

**Style.** JavaScript with JSX, no TypeScript. Tailwind classes in the markup; shared tokens
in `src/index.css`. ESLint with zero warnings allowed. Exact dependency versions in
`package.json`. Imports use the `@/` alias for `src/`.

**Accessibility.** Every control is reachable by keyboard and has a visible focus ring and
an accessible name; streamed text is announced through a live region; motion respects
`prefers-reduced-motion`.

## Text

Interface text and error messages are short, plain sentences that say what happened and
what to do next. The same goes for commit messages and docs.

## Commits and branches

- Branches: `feat/…`, `fix/…`, `perf/…`, `docs/…`, from `dev`.
- One line, imperative, sentence case, saying what changed:
  `Add two-factor sign-in for staff`, `Limit open access to thapar.edu addresses`.
- One concern per commit, each passing the tests on its own.
